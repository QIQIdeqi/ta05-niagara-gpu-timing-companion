TA15 · Niagara first-frame mismatches in MRQ

Use a shot you can re-render. The author's comparison used UE 5.8.4 and D3D11. Treat the frame ranges below as a worked example and record the equivalent ranges for your own shot.

1. Build a shot that exposes the difference

  1. Place a camera and a Niagara Actor in a test level. Choose a CPU system with a visible trail or particles that survive across several output frames. Use a simple background.
  2. Create a Level Sequence, bind the camera in Camera Cut, and add a Transform track for the Niagara Actor. Scrub the timeline and verify that the emitter source in the current level actually moves.
  3. Use a camera cut range of [38,90). Key the emitter source at Y = −140, 0, and 0 cm on frames 38, 54, and 58. Keep the other axes fixed. Preserve interpolation and camera settings between runs. Check that particles are visible before frame 54 and that the preceding motion changes their trail.
  4. Give every run a separate output folder. Use absolute frame numbers in filenames. Record the engine version, camera, rendering backend, output range, and sampling settings.

2. Compare live simulation warm-up

Use 640×360 PNG output at 60 fps, 240 ticks/s, a centered shutter, Motion Blur 0.5, one spatial sample, two temporal samples, and AA None. The test used a 120° FOV. Keep Render Warm Up Frames off.

The camera-cut group sets Engine Warm Up Count to 0 and enables Use Camera Cut for Warm Up. MRQ derives warm-up from the Camera Cut section before output begins. The 0 in the table is the configured value. In the v0.3 same-machine rerun, the MRQ initialization log reported 16 warm-up frames for both L1 and L2. L1 used a configured count of 16; L2 used a configured count of 0 and derived its warm-up from the camera cut. The equal counts do not imply identical sequence evaluation.

Check the camera and temporal-sampling logs, then compare frame 54 of each short render with frame 54 of the continuous reference. Engine warm-up advances the engine. Camera-cut warm-up also evaluates the sequence before output starts. Assess render history and depth-dependent GPU particles separately from this CPU example.

3. Compare playback at cache entry

  1. Record the test system with a Niagara Sim Cache track in Sequencer. Render the full section once and confirm that the target frames show the expected particles.
  2. Duplicate the sequence twice and keep the same cache asset and track binding. Use [0,59) for the full section (C0) and [56,59) for both short sections. Give both short sections the Repeat setting and a first-loop offset of 224 ticks.
  3. Use Display Cache Only for C1 and Sim Without Cache for C1Live. Where there is no cache data to display, the former disables the component and the latter runs ordinary simulation. Render frames 54–57 for all three conditions.
  4. Compare each frame with the same frame in C0. In this test, C1 and C1Live differed from C0 at 103 and 593 foreground pixel positions on frame 56, and 132 and 11 on frame 57. Re-measure when you change the emitter or shot.

4. Record enough detail for a repeat run

Use PNGs of equal dimensions and apply the same foreground rule to both. For this footage, green channel > 30 marks a foreground pixel. Count the positions marked foreground in exactly one mask. Inspect the original images and masks before interpreting the total.

Record the condition, absolute output frame, reference condition, foreground count, differing pixel count, and run order. Reopen the editor and repeat in a different order. If runs disagree, check bindings, output folders, frame numbers, and cache settings first. Component age, activation state, and GPU cost each require separate measurements.

Self-check. Pick the closer mode using frame 57 alone. Then read frame 56 and revise your conclusion to name the output frame and the reference condition.
